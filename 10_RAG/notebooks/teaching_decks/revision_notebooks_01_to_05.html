Notebook 02 + 03 · Chunking

Six ways to cut text, each one a bit smarter

1Fixed sizeCuts blindly, even through a table
2RecursivePrefers paragraph and line breaks
3SemanticCuts where the topic actually shifts
4Sentence windowMatch small, hand back the neighbours
5Parent / small-to-bigMatch a child, return its parent section
6Document-type awareCode, Markdown and HTML each split on their own structure
Framework note: strategies 4 and 5 needed manual wiring in LangChain. In LlamaIndex, SentenceWindowNodeParser and HierarchicalNodeParser do the same job in one line. That is where LlamaIndex earns its keep.

Notebook 04 · Embeddings

Meaning, turned into distance

"How do plants make food using light" and "Photosynthesis converts sunlight into glucose" share almost no words, yet they sit close together once embedded. An unrelated sentence sits far away.

The one non-negotiable rule
Index and query must use the exact same embedding model. Swap models mid-way and the "nearest neighbour" stops meaning anything.
language coverage context window dimensions vs cost domain fit

Notebook 05 · Vector databases

Same search, three levels of who runs it

FAISS
library, not a database
We built the HNSW graph and the IVF clusters ourselves, to see the mechanics.
Chroma
embedded database
Same HNSW core, plus metadata filters and persistence, zero infrastructure.
Pinecone
managed service
Someone else runs the infrastructure. You pay for that in cost and lock-in.
efSearch (HNSW) and nprobe (IVF) are the dials. Turn them up: recall climbs toward the exact-search line, latency climbs with it. Every vector database is tuning this same trade-off underneath.
