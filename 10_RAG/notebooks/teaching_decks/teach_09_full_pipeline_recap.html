Station 02 · Ingestion & Chunking

Parsing decides what's even possible to retrieve

A table read as flat text loses its meaning before chunking ever begins. Once parsing is right, six chunking strategies compete on the same tradeoff: precision vs. context.

01
Fixed size
Cuts blindly, even through a table row.
02

Semantic

Sentence window
Match small, hand back the neighbours.

Parent / small-to-big
Match a child, return its parent section.
06
Doc-type aware
Code, Markdown, HTML each split on their own structure.
Small chunk (≈150 tok)
High precision, narrow context. Risk: the retrieved sentence has lost the paragraph that explains it.
Large chunk (≈1500 tok)
Broad context, diluted embedding. Risk: the vector represents three topics blended into one average.

Station 03 · Frameworks

Same lesson, two toolkits

We built the same ingestion and chunking pipeline twice: once in LangChain, once in LlamaIndex. The parser mattered. The framework mostly didn't, except for one thing.

LangChain
notebook 02 · manual wiring
  • Explicit loaders + splitters, composed by hand
  • Sentence-window & parent-child needed custom code
  • Maximum control, more boilerplate
LlamaIndex
notebook 03 · batteries included
  • SentenceWindowNodeParser in one line
  • HierarchicalNodeParser builds parent/child automatically
  • Less code for retrieval-specific node structures
Takeaway: the parser and chunking strategy decide retrieval quality. The framework just decides how much code it takes to get there. LlamaIndex earns its keep on the hierarchical and windowed node parsers.

Station 04 · Embeddings

Meaning, turned into geometry

"How do plants make food using light" and "Photosynthesis converts sunlight into glucose" share almost no words, yet they sit close together once embedded. An unrelated sentence sits far away.

Broken #1 · different dims Broken #2 · same dims, wrong model
The one non-negotiable rule
Index and query must use the exact same embedding model. Swap models mid-way and nearest neighbour stops meaning anything, because the two vector spaces no longer line up.

Station 06 · Sparse Retrieval

The keyword matcher that refused to die

We already had dense embeddings. So why does every major search engine still run a keyword scorer underneath? Because raw counts have no ceiling, and BM25 fixes that.

Stuff a keyword 50 times into a document and TF-IDF's score keeps climbing forever. BM25 caps the benefit of repetition and normalizes for document length, which is why it beat TF-IDF in production search. SPLADE goes a step further: a learned sparse model that still keeps BM25-style term matching inside it.

Station 07 · Hybrid Search

Two retrievers, one blind spot each

Across 16 real queries, dense and sparse each won on different questions, and each went completely blind on the other's home turf.

Sparse · blind to meaning
Query "heart attack" scores 0.000 against a document that only says "myocardial infarction." Zero shared tokens, zero score, no matter how relevant the document actually is.
Dense · fuzzy on exact terms
Ask for an exact product code or error string and embeddings blur it into "something similar," when you needed the literal match.
Naively summing BM25 and cosine scores fails, because the two live on completely different scales. Reciprocal Rank Fusion fuses on rank position instead of raw score. Across all 16 test queries, hybrid beat both single-stage retrievers on every metric.

Station 08 · Reranking

Fusion gets it into the list. Reranking puts it on top.

Same transformer architecture, two completely different jobs: encode once vs. compare directly.

Bi-encoder
pass 1 · done ahead of time
Query and document are embedded independently, then compared by cosine similarity. Fast enough to search millions of chunks, but the two texts never actually "see" each other.
Cross-encoder
pass 2 · done at search time
Query and document are fed into the transformer together, so self-attention can directly model word-to-word interaction. Far more accurate, far slower, so it only runs on the top 20–50 fused candidates.
Cross-encoder · pointwise FlashRank · CPU-only Cohere Rerank · managed API ColBERT · late interaction RankGPT · listwise LLM
